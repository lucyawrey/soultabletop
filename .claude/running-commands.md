# Running commands: background

Moved out of `CLAUDE.md` so it is read only when needed. `CLAUDE.md` keeps the summary and the hard rules.

- Node comes from nvm (`.nvmrc`) and pnpm from corepack (`packageManager` in `package.json`); there's no system Node. Run node/pnpm through `.claude/scripts/agent-run.sh <command>` (e.g. `.claude/scripts/agent-run.sh pnpm check`). It runs from the repo root (so pass absolute paths for anything outside it, e.g. `npm i --prefix <scratchpad> …`), loads nvm from `$NVM_DIR` (default `~/.nvm`), Arch's `/usr/share/nvm`, or Homebrew's `nvm`, runs `nvm use`, and falls back to a zsh login shell if none of those work. Both of the user's machines are covered: Linux (CachyOS; fish is the interactive shell, nvm is the pacman package, agent shells run zsh) and a Mac.
- Staying on Node and pnpm, not Bun: a spike (2026-09-29) found Bun can't read pnpm 12's lockfile, `nuxt build` ran slower under Bun than Node on the same packages (~43 s vs ~32 s), and the built server showed no runtime gain for this database-bound app; Vercel's Bun runtime is also still beta.
- pnpm keeps its default symlinked `node_modules`. The hoisted layout (`nodeLinker: hoisted`) cut local builds from ~55 s to ~32 s, but Vercel's install then fails ("the installed pnpm wrapper is missing" while its pnpm switches to the `packageManager` version), so it was dropped. An untried fix is Vercel's `ENABLE_EXPERIMENTAL_COREPACK=1`; the ESLint rule `import/no-extraneous-dependencies` (on since #45, checks `package.json`, not `node_modules`) would keep catching undeclared imports under a hoisted layout.
- Cloud sessions: a fresh clone has no `.env.local` (it's gitignored and holds live secrets), so anything that needs the database (dev server, `pnpm db:*`, `pnpm admin:set`, API checks) won't work until the environment provides `DATABASE_URL` and `BETTER_AUTH_SECRET`; typecheck, lint, tests, and template compilation work without them.
- Browser checks: on Linux, Chromium's headless shell is installed in Playwright's cache (`~/.cache/ms-playwright`; on a Mac the cache would be `~/Library/Caches/ms-playwright`), which persists across sessions. The Mac uses Google Chrome instead: launch with `channel: "chrome"`. Install `playwright-core` in the session's scratchpad (`.claude/scripts/agent-run.sh npm i --prefix <scratchpad> playwright-core`), run scripts with `NODE_PATH=<scratchpad>/node_modules`, and `chromium.launch()` finds the cached browser; if a newer `playwright-core` wants another browser revision, run `npx playwright-core install chromium-headless-shell` again. Scratchpad scripts reach project packages (e.g. `pg`) with `createRequire("<repo>/package.json")`. Use `withSmokeUser` from `.claude/scripts/smoke-session.mjs` for throwaway `claude-smoke-*@example.invalid` users: it registers, signs in, hands you the session cookie, and deletes the user afterwards (run with `node --env-file=.env.local`); delete only users you created. Listen for console errors: Vue hydration mismatches only show there. The helper deletes the user but **not resources it owns**, so delete what you create through the API before its callback ends (older sessions left about 50 smoke users in the test database, one still owning resources; the database reset in `TODO.md` clears them). To look at your real resources read-only instead, send your API key: `.env.local`'s `SOUL_TABLETOP_API_KEY` in an `x-api-key` header through Playwright's `extraHTTPHeaders` shows pages as you, with no throwaway user.
- Checking UI work: `pnpm check` and `pnpm check:templates`, then a dev server on a spare port (the user's runs on 3000 or 3001; check with `lsof -iTCP -sTCP:LISTEN -P | grep node`) started from the worktree with `.claude/scripts/agent-run.sh pnpm nuxt dev --dotenv <main checkout>/.env.local --port 3005`, and Playwright screenshots of signed-out pages and of signed-in pages via `withSmokeUser`. Start it with Bash's `run_in_background` and the longest `timeout` (7200000 ms): the 30-minute default stops it mid-run, and a smoke user whose callback was cut off is left behind with its resources (delete those rows, then the user). Stop the dev server you started. On a fresh dev server the first load of a page can fail with Vite's "504 Outdated Optimize Dep" plus a hydration warning; reload, it's not the app. After adding components or `app/utils` files, the server can serve stale auto-imports (hydration warnings or "x is not a function"); restart it.
