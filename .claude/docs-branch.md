# Docs branch

Moved out of `CLAUDE.md` so it is read only when needed. `CLAUDE.md` keeps the summary and the hard rules.

`docs` is a permanent branch, normally checked out in the main checkout (there is no separate docs worktree), that collects changes which aren't part of a feature: `TODO.md` items, `.claude/HANDOFF.md`, `.claude/CLAUDE.md` and skill changes, and other standalone notes. Text that documents code in a feature PR (`docs/sheet-system.md`, OpenAPI text, README facts about a feature) ships in that PR, not here. The main checkout sits on `docs` and is switched to `main` when the user needs to run the app, test, or merge (see "The user's checkout").

- **The user's checkout:** the user keeps the main checkout on `docs` (open in VS Code to read), so they can read and edit `TODO.md`, `.claude/HANDOFF.md`, `.claude/CLAUDE.md`, and skills directly and commit them with plain git. They `git switch main` (kept up to date with `git fetch origin main:main` or a pull) when they need to run the app, test, or merge, and back afterwards; agents may switch too, but only on a clean tree. Their edits are a writer too: they may be uncommitted at any time. Before touching files on `docs` an agent runs `git status`; it stages only its own files (never `git add -A` or `git commit -a` over changes it didn't make), never discards, stashes, resets, or overwrites the user's changes, re-reads a file just before editing it, and doesn't run `git merge origin/main` on a dirty tree: it asks the user to commit or tell it to proceed. The user commits their own edits, or asks an agent to. When the checkout is on `main`, its `TODO.md` and `HANDOFF.md` are older copies: read the current ones with `git show docs:TODO.md`.
- **Writing:** the user or an agent commits on `docs` in the main checkout, one writer at a time (check `git status` first; if the checkout is on another branch, ask before switching). The coordinator owns `HANDOFF.md`. An agent in its own worktree that wants a TODO item or rule recorded tells the coordinator, or commits it on `docs` if nobody else is using the checkout. Keep commits small and one topic each, so any of them can be moved on its own. Commit messages follow the usual rules.
- **Reading:** the `docs` branch has the current `TODO.md` and `HANDOFF.md`; `main`'s copies may be older. A session starting work reads them from there (`git show docs:TODO.md` when the checkout is on `main`) (or `origin/docs` if it isn't on the same machine). Rule changes in `CLAUDE.md` don't reach other worktrees until they merge, since those are cut from `main`, so anything an agent must follow right now goes in its brief too.
- **Reaching `main`:** a docs commit merges by being carried by a feature PR or by a docs-only PR. When a feature PR is about to open, the coordinator may `git cherry-pick <sha>` the relevant docs commits onto that feature branch so they merge together. When no feature PR is open (or the docs branch has had unmoved commits for a while), open a docs-only PR from `docs`. Each commit goes to `main` once.
- **Updating after a merge:** PRs are squash-merged, so a cherry-picked commit lands on `main` as part of the feature commit and the original is still on `docs`. After any merge that carried docs commits (or a docs-only PR), run `git fetch origin && git merge origin/main` on `docs`. The carried changes are identical on both sides, so they merge cleanly and drop out of `git diff origin/main`, which then shows only what hasn't reached `main` (`git log origin/main..docs` still lists the old commits; ignore it). Merge, don't reset or rebase, so `docs` is never rewritten and never needs a force-push. A conflict in `TODO.md` or `CLAUDE.md` keeps both sides' additions.
- **Pushing:** like every branch (see "Git workflow" in `CLAUDE.md`), `docs` may be pushed without asking after `scripts/check-secrets.sh` passes (in other git commands write `refs/heads/docs` or `origin/docs`, since plain `docs` also names the `docs/` folder). A force-push of `docs` still needs approval (it shouldn't be needed). A pushed `docs` branch makes the current `TODO.md` and `HANDOFF.md` readable from another machine without merging. Vercel builds a preview for every pushed branch, which a docs-only push doesn't need. Opening the docs-only PR is a separate step: tell the user when one is ready rather than opening it unprompted.
- **GitHub and branch deletion:** the repo deletes a PR's head branch on merge, which would delete the remote `docs` branch after a docs-only PR. A GitHub ruleset named "Docs" restricts deletions on `docs` only, to prevent that; it leaves pushes and force-pushes allowed, and the separate "Main" ruleset is unchanged. If the remote branch is ever deleted anyway, recreate it by pushing `docs` again.
