# Docs branch

Moved out of `CLAUDE.md` so it is read only when needed. `CLAUDE.md` keeps the summary and the hard rules.

`docs` is a permanent branch, kept in its own worktree at `../soultabletop-worktrees/docs`, that collects changes which aren't part of a feature: `TODO.md` items, `.claude/HANDOFF.md`, `.claude/CLAUDE.md` and skill changes, and other standalone notes. Text that documents code in a feature PR (`docs/sheet-system.md`, OpenAPI text, README facts about a feature) ships in that PR, not here. The main checkout stays on `main`; the user's main VS Code window normally shows the docs worktree instead (see "The user's window").

- **The user's window:** the user's main VS Code window normally has the docs worktree open (`/home/lucy/Developer/soultabletop-worktrees/docs` on the CachyOS machine), so they can read and edit `TODO.md`, `.claude/HANDOFF.md`, `.claude/CLAUDE.md`, and skills directly. They switch that window to the main checkout (kept on `main` and up to date) when they need to run the app, test, or merge, and back afterwards. Their edits are a writer too: they may be uncommitted at any time. Before touching the docs worktree an agent runs `git status`; it stages only its own files (never `git add -A` or `git commit -a` over changes it didn't make), never discards, stashes, resets, or overwrites the user's changes, re-reads a file just before editing it, and doesn't run `git merge origin/main` on a dirty tree: it asks the user to commit or tell it to proceed. The user commits their own edits, or asks an agent to. The main checkout's `TODO.md` and `HANDOFF.md` are older copies: read the current ones from the docs worktree.
- **Writing:** the user or an agent commits in the docs worktree, one writer at a time (check `git -C ../soultabletop-worktrees/docs status` first). The coordinator owns `HANDOFF.md`. An agent in its own worktree that wants a TODO item or rule recorded tells the coordinator, or commits it in the docs worktree if nobody else is using it. Keep commits small and one topic each, so any of them can be moved on its own. Commit messages follow the usual rules.
- **Reading:** the docs worktree has the current `TODO.md` and `HANDOFF.md`; `main`'s copies may be older. A session starting work reads them from there (or `origin/docs` if it isn't on the same machine). Rule changes in `CLAUDE.md` don't reach other worktrees until they merge, since those are cut from `main`, so anything an agent must follow right now goes in its brief too.
- **Reaching `main`:** a docs commit merges by being carried by a feature PR or by a docs-only PR. When a feature PR is about to open, the coordinator may `git cherry-pick <sha>` the relevant docs commits onto that feature branch so they merge together. When no feature PR is open (or the docs branch has had unmoved commits for a while), open a docs-only PR from `docs`. Each commit goes to `main` once.
- **Updating after a merge:** PRs are squash-merged, so a cherry-picked commit lands on `main` as part of the feature commit and the original is still on `docs`. After any merge that carried docs commits (or a docs-only PR), run `git fetch origin && git merge origin/main` in the docs worktree. The carried changes are identical on both sides, so they merge cleanly and drop out of `git diff origin/main`, which then shows only what hasn't reached `main` (`git log origin/main..docs` still lists the old commits; ignore it). Merge, don't reset or rebase, so `docs` is never rewritten and never needs a force-push. A conflict in `TODO.md` or `CLAUDE.md` keeps both sides' additions.
- **Pushing:** the user has given standing approval to push `docs` (and only `docs`) without asking each time, after the usual secrets check (compare the commits to be pushed against `.env.local` values without printing them, and grep for connection strings and key prefixes). Any other branch still needs the user's approval every time, and a force-push of `docs` would too (it shouldn't be needed). A pushed `docs` branch makes the current `TODO.md` and `HANDOFF.md` readable from another machine without merging. Vercel builds a preview for every pushed branch, which a docs-only push doesn't need. Opening the docs-only PR is a separate step: tell the user when one is ready rather than opening it unprompted.
- **GitHub and branch deletion:** the repo deletes a PR's head branch on merge, which would delete the remote `docs` branch after a docs-only PR. A GitHub ruleset named "Docs" (created 2026-09-30 with `gh api`) restricts deletions on `docs` only, to prevent that; it leaves pushes and force-pushes allowed, and the separate "Main" ruleset is unchanged. This held for the first docs-only PR (#32). If the remote branch is ever deleted anyway, recreate it by pushing `docs` again.
