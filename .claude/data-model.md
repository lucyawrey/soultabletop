# Data model

Moved out of `CLAUDE.md` so it is read only when needed. `CLAUDE.md` keeps the summary and the hard rules.

- Everything user-created is a row in the polymorphic `resource` table (`kind`: `system`, `campaign`, `contentType`, `sheet`, `content`) plus a per-kind table keyed by `resourceId`. Resources are owned by a user or a group, with extra access via `resourceGrant`.
- **Official vs Community**: groups have a `kind`; `system` groups are official. Resources owned by a system group are "Official", everything else "Community" (future UIs, e.g. search, label results this way and rank Official first). The seeded system group is "Soul Tabletop" (readable ID `soul`); site admins can create more (`official: true` on group create). Site admins see and manage system groups without being members (`getGroupAccess` / `requireGroupViewer` / `requireGroupAdmin` in `server/utils/group.ts`), and system groups are exempt from the keep-one-admin rule.
- **Site admins** (`user_profile.role = 'admin'`) can read and delete anything and edit official resources, on top of normal access to their own and their groups' resources (tests in `server/utils/resource-access.test.ts`). Make one with `pnpm admin:set <username>` (`--remove` to undo); it needs database access, which is the point: there is no in-app way to become an admin.
- **Authentication**: routes find their user with `getAuthenticatedUser` / `requireAuthenticatedUser` (`server/utils/auth.ts`), never by reading the session themselves: they take the session cookie, else a user API key (`Authorization: Bearer` or `x-api-key`, Better Auth's API key plugin, `apikey` table), and refuse Read Only keys on anything but GET/HEAD/OPTIONS, so that check covers every route through them. A key that is sent but doesn't work is a 401, never a fall back to logged out. Routes a key must never reach (managing API keys) use `requireSessionUser`. The plugin's own `/api/auth/api-key/*` routes are disabled (`disabledPaths`); keys are managed through `/api/profile/api-keys`. Better Auth's server-side `auth.api` calls need the request's headers (there is no fixed base URL to fall back on), and the API key plugin treats a call with headers as a client call that can't set server-only fields such as `permissions`, which is why the access level is written to the row after creating the key. Access levels are stored as plugin `permissions` (`server/utils/api-key-rules.ts`); anything unexpected counts as read-only. Sessions are cached in a signed cookie for 5 minutes (Better Auth `session.cookieCache`, `SESSION_CACHE_MAX_AGE` in `server/utils/session-cache.ts`), so a revoked session or a changed name or email can lag that long where the cookie is used. Access decisions never come from it: the site role and group and campaign roles are read from the database on every request. `getAuthenticatedUser` passes a rewritten cache cookie on to the response. The session token cookie is passed on only on Better Auth's daily session extension, and only when it re-sets the exact token the request sent. Once a response renews the token, no cache cookie is passed on for the rest of that request, so one response landing after sign-out can't sign the user back in; two overlapping late responses still can, for up to 5 minutes (`sessionSetCookiesToForward` in `server/utils/session-cache.ts`). Page loads look the session up on the page request itself (`server/middleware/session-renewal.ts`, filtered by `isPageLoad`), since cookies set by internal calls during server rendering never reach the browser; `requireSessionUser` and Better Auth's own sensitive routes check the session in the database. A page that changes the user must refresh with `authClient.getSession({ query: { disableCookieCache: true } })`, as `/profile` does. List endpoints leave out the heavy columns (sheet `markup`/`cssStyles`, content type `schema`, content `data`; `server/utils/list-columns.ts`); fetch the single resource for them. `SERVER_TIMING` (README) adds a `Server-Timing` header with database time and query count: on in dev, off in production unless set.
- Access is computed by `getResourceAccess` in `server/utils/resource-access.ts` (`canRead`/`canEdit`/`canDelete`); use `getResourceAccessOrPublic` (with a `null` context) on routes that allow anonymous visitors, who can read only Public, non-hidden resources. `requireResourceReader`/`requireResourceEditor` in `server/utils/resource-management.ts` wrap this for single-resource routes. Resources are addressable by UUID or by owner + readable ID (`/api/<kind>/<owner>/<readableId>`): every resource `[id]` route (and the campaign member routes) calls `resolveResourceRouteId` (`server/utils/resource-address.ts`) right after finding the user, then continues on the UUID with its usual checks; the owner-first SQL in `findReadableResourceId` includes the read rule, and a missing owner, a missing resource, and an unreadable one all give the same 404, including for PATCH and DELETE. Single GETs return `ownerReadableId`, and `GET /api/resource/lookup` returns `{ id, kind, systemId }` under the same access check (the current-system middleware uses it). New resource routes must use the resolver. Readable IDs that equal a fixed URL segment (a sheet `edit`, a campaign `members`) are not reserved and keep working only by UUID.
- List and single-resource GET endpoints return `canEdit`; the UI hides edit/delete when it's false. Keep this pattern for new resource endpoints.
- Characters and Content are both `content` resources, split by the ContentType's `contentCategory`: Characters pages show `playerCharacter` and `nonPlayerCharacter`, Content pages `general` and `page`. The category list, the two sets, and their UI labels live in `shared/content-categories.ts` (the Drizzle enum is built from it); use them rather than repeating category checks. Lists are filtered client-side from `/api/content`; no separate Characters API.
- Content types have `showSheetWarnings` (default off): with a non-strict schema, the Sheet editor's warnings about field paths not in the schema are shown only when it's on; structural errors always show. Only the sheet's root content type's flag counts (`validate()` in `shared/sheet/validate.ts`). Switching a type from strict to non-strict turns it on unless the request sets it (`resolveShowSheetWarnings` in `shared/content-schema.ts`).
- A ContentType's default Sheet belongs to the ContentType: changing a Sheet's `isDefault` requires edit access to its ContentType, not just the Sheet. Making a Sheet the default when another Sheet already is returns 409 (`assertDefaultReplacementConfirmed` in `server/utils/sheet-schemas.ts`, naming the current default only if the user can read it) unless the body has `confirmReplaceDefault: true`; the UI shows `ReplaceDefaultSheetAlert` and resends. Replacing the generated default (no default Sheet row) needs no confirmation.
- User profiles have a `username` (readable-ID format, unique, case-insensitive, stored lowercase, at most 40 characters, `MAX_USERNAME_LENGTH`). The display name is Better Auth's `user.name`: optional and not unique, and it defaults to the username as typed at sign-up (keeping its capitalization). It is required in storage, so an empty one is stored as the username (`resolveDisplayName` in `shared/display-name.ts`), is at most 100 characters, and can't contain control, invisible, or text-direction characters (`getDisplayNameError`; also enforced by a Better Auth `databaseHooks` check, and Better Auth's own `/sign-up/email` and `/update-user` routes are disabled, so users are made by `/api/register` and edited by `/api/profile`). While the name is still the old username it follows a username change, in the same transaction; `PATCH /api/profile` takes `name` (empty or `null` resets it) and updates the `user` row directly, and the profile page then refreshes the session and `useProfile`. Where people must tell users apart, show the username with the name (`formatUserLabel`, "Name (@username)"; the user menu and member tables show both).
- Field types: `string`, `number`, `boolean`, `scalar` (one string/number/boolean/null, never nested), `resourceLink`, `array` (`itemType`), `struct` (structured: exactly its `entries`, strictness applies inside), `object` (free-form: any nested values, keys must be identifiers at every level, not checked otherwise; sheets edit it as JSON and paths into it only warn), `content`.
- ContentType schemas (`ContentFieldSchema` in `shared/content-schema.ts`, TypeBox mirror `contentTypeSchemaSchema` in `server/utils/api-schemas.ts`; keep both in sync) are stored as `json`, not `jsonb`, to keep field order. Every ContentType has a built-in `name` field that is the Content's resource name: schemas can't define `name`, and a `name` key in submitted Content data is moved to the resource name (`extractDataName`).
- A `content` schema field holds either the ID of existing Content of `contentTypeId` (a reference) or an object of local data validated against that ContentType (with its own `name`); `allow` restricts which. A `resourceLink` field holds the ID of any resource the saving user can read (system, campaign, content type, sheet, content), or only of its optional `kind`; content GET returns the viewer's readable ones as `links` (`{ [id]: { name, kind } }`, loaded by `loadContentRefs`), and sheets show them as links to the resource's page. `validateContentData` in `server/utils/content-validation.ts` is async because it checks references and loads referenced schemas.
- Schemas are edited with the schema builder on `/types/[id]` (`SchemaBuilder` in `app/components/schema/`, drag-and-drop via SortableJS `useSortable`, one handle class per nested list), with a JSON view as the advanced option. The builder shows the schema's own names (types, properties like `entries`/`itemType`/`contentTypeId`, `allow` and `kind` values), never friendlier substitute words, since it edits the data format directly; `schemaDisplayName` only spaces and capitalizes them (`resourceLink` → "Resource Link"). Its framework-free model (schema ⇄ ordered rows with stable ids, key checks, JSON shape check) is `shared/schema-builder.ts`. Create dialogs never take raw JSON: they ask for the basics and open the new resource's page. Content created without `data` starts from `defaultContentData` (empty values for required fields) and skips "is required" for required reference fields, which start empty.
- Content PATCH accepts `expectedUpdatedAt` and returns 409 if the Content changed since; the returned `updatedAt` can be sent back as the next `expectedUpdatedAt`.
- Code shared by client and server lives in `shared/`; server code imports it with relative paths (drizzle-kit loads `server/database/schema.ts` without Nuxt aliases).
- The Sheet system (markup language, rendering, editing, CSS) is designed in `docs/sheet-system.md`; follow it and update it when a decision changes. Framework-free logic (parser, tag registry, validator, generator, runtime path resolution, CSS scoping) is in `shared/sheet/` with vitest tests; Vue components are in `app/components/sheet/` (`SheetRenderer`, one component per layout tag, `Field`/`FieldInput` for all field tags); the Sheet editor is `/sheets/[id]/edit` (CodeMirror, client-only). When adding a tag, add it to `shared/sheet/registry.ts` and render it in `sheet/Node.vue` (layout) or `sheet/Field.vue` + `sheet/FieldInput.vue` (fields).
- `sheet-*` classes are hooks for Sheet CSS, not Tailwind (ESLint ignores them).
