# Conventions

Moved out of `CLAUDE.md` so it is read only when needed. `CLAUDE.md` keeps the summary and the hard rules.

- **Team copy**: `content/` (repo root, not `public/`) holds source files the site pulls in at build time, such as YAML now and Markdown later; it is not for static assets. The site title and description, the signed-out home text, and the dashboard heading are in `content/copy.yml` (YAML, comments allowed, loaded by `@rollup/plugin-yaml`), read through the typed `copy` object in `app/utils/copy.ts`; `{name}`-style markers are filled with `fillCopy`. New team copy goes there, not inline in a component; the file's shape is declared in `shared/yaml.d.ts`, so add a key in both and in `shared/copy.test.ts`. Placeholders (see "User-facing copy" in `CLAUDE.md`) go into the YAML value with a `# Copy:` comment.
- **Enum values** (Drizzle `pgEnum` and matching TypeBox `Type.Literal`s) are camelCase: single words lowercase (`admin`, `gm`, `general`), multi-word lowerCamelCase (`nonPlayerCharacter`, `playerCharacter`, `contentType`).
- **Theme**: one light theme, no dark mode; read `docs/theme.md` before changing colors, fonts, or component defaults. Colors are defined only in `app/assets/css/main.css` (palettes, then Nuxt UI's `--ui-*` roles, then the `--st-*` Sheet tokens), and `shared/theme.test.ts` checks their contrast. In components, use Nuxt UI's semantic classes (`text-muted`, `bg-elevated`, `border-accented`, `text-primary`), never raw palette colors or hex values. `--ui-border` is for dividers only; control outlines use `ring-accented`/`border-accented` (3:1). State never depends on color alone, and the display font (`font-display`) is only for headings at 22px and up. The `--st-*` names are a stable contract for published sheets: never rename or remove one (list in `shared/sheet/theme-tokens.ts`).
- **Readable IDs**: resources and groups have a `readableId` (lowercase letters, numbers, and hyphens), labeled **"ID"** in the UI. In code, API fields, and docs, "ID" or `id` alone means the UUID primary key, never the readable ID; never call it "slug" in the UI. Forms use `<ReadableIdField>`, fed by `useReadableIdFromName` (auto-generates from Name until the user edits it; pass a key like `"username"` for other field names; create dialogs for resources in a system pass a prefix getter, `useSystemIdPrefix`, so generated IDs start with the system's ID, shortened by `systemIdPrefix` in `shared/system-id-prefix.ts` when longer than 8 characters: `pathfinder-2e` → `p2e-strength`), which shows `readableIdError` inline via `UFormField :error`. `getReadableIdError` returns `undefined` when valid — never `""`, because `UFormField`'s `error` prop is `[Boolean, String]` and Vue casts `""` to `true`, marking the field as errored. Forms show live "available / in use" hints: `ReadableIdField` takes an `availability` prop fed by `useResourceIdAvailability` (`app/composables/useReadableIdAvailability.ts`), which calls `GET /api/readable-id-availability` (authenticated; the owner is checked with `resolveResourceOwner`, and a `resourceId` needs edit access, group admin for groups, so it never reveals IDs under owners the caller can't create for); sign-up and the profile page use the public `/api/profile/username-availability`. A taken result only blocks the sign-up form; elsewhere the server's 409 stays authoritative. Usernames and group readable IDs share one namespace, guaranteed by the `owner_readable_id` table (migration 0012, kept current by hand-written triggers on `user_profile.username` and `group.readable_id`, which drizzle-kit does not model; a clash is a 23505 mapped to 409). Check availability with `isOwnerReadableIdTaken` (`server/utils/owner-readable-id.ts`), never by querying one table.
- **Visibility**: `isPubliclyReadable` is always labeled "Visibility" in the UI, with values **Public** (true) and **Limited** (false) — never "Private", since non-public Resources can still be shared. Use `visibilityLabel()` (`app/utils/visibility.ts`) for text, `<VisibilityBadge>` in list tables (every resource list has a Visibility column), and `<VisibilityField v-model>` in forms. Create forms put `<OwnerField v-model="form.ownerGroupId">` right before Visibility; it offers "You" plus groups where the user is an admin or editor and hides itself when there are none. Create endpoints resolve the owner with `resolveResourceOwner` (`server/utils/resource-management.ts`), which allows group admins/editors, and site admins for system groups they aren't in (matching what `OwnerField` offers).
- **Dialog field order**: every create and edit dialog keeps its fields in one order, so the same field sits in the same place everywhere: Name, ID, System, Type, the kind's own fields, then Owner and Visibility last (above the error alerts; in content settings above the advanced Data (JSON) editor). Create dialogs start on the header's system (`useCurrentSystem`). Dialogs that pick a content type (sheets, characters, content) use `useSystemTypePicker` (`app/composables/useSystemTypePicker.ts`): a System select listing the systems with a type to offer, then a Type select narrowed to that system, preselecting the system's most used type in the dialog's categories (`GET /api/most-used-content-types`, which counts content site-wide and returns only types the caller can read).
- **Changing the owner**: every resource PATCH accepts `ownerGroupId` (a group, or `null` for the acting user), handled by `resolveOwnerChange`. Only the owning user, admins of the owning group, or site admins may move a resource (`canChangeResourceOwner`; single GETs return it as `canChangeOwner`), and the target group needs them as admin or editor (or, for site admins, to be a system group). Detail pages and the sheet editor show `<OwnerField :original>` when `canChangeOwner` is true; it warns when moving to a group, and pages send `ownerGroupId` only when it changed. Readable IDs are unique per owner and kind, so PATCH handlers map conflicts to 409 with `rethrowReadableIdConflict`. Every resource kind accepts `isPubliclyReadable` on create and update; new Resources default to Limited.
- **List pages and search**: list endpoints (`/api/system`, `content-type`, `sheet`, `content`, `campaign`) take `q` (name/ID search), `scope` (`mine`: owned by the user or their groups, a campaign they're a member of, or shared with them to edit; `public`), and `page`. With `page` they return `{ items, total, page, pageSize }` (25 per page, `shared/resource-list.ts`); without it the plain array of everything readable, which pickers and dropdowns use. Logic is in `listResources` (`server/utils/resource-list.ts`): every scope filters, counts, and pages in SQL, using the read and My-list rules in `server/utils/resource-access-sql.ts` (viewer facts as subqueries, grants via `EXISTS`; never bind lists of IDs from the whole site), and each returned row is still checked with `getResourceAccess`. When an access rule changes, change `getResourceAccess`/`isListed`, the SQL rules, and their transcription in `resource-list-filter.test.ts` together; that test checks all three agree, and the opt-in `resource-access-sql.db.test.ts` checks the real SQL against the code rules on the database. Rows and single-resource GETs carry `source` (`official`, `you`, `yourGroups`, `shared`, `community`, in that precedence, so members of a system group still see its resources as Official (user's decision, 2026-10-05); labeled You, Group, Official, Shared, Community: one word each, `RESOURCE_SOURCE_LABELS`; Shared means a grant reaches the viewer or they're a member of the campaign; logged-out viewers get only Official/Community; `getResourceSource`) and sort Official first. Find leaves out what My lists when signed in with no search text (`excludesMineFromFind`), so a search is how you find your own things there. `/api/content` also takes `categories` (comma-separated). Pages use `useResourceList` (tab, `q`, `page` kept in the URL; logged-out visitors get only Find) inside `<ResourceList>`, and show `<SourceBadge>` (Official/Community). Campaign "mine" also includes campaigns the user is a member of. `/api/content` lists only content whose content type the viewer can read. The pure filtering rules are in `server/utils/resource-list-filter.ts` (tested).
- **API errors in forms**: every form/delete `catch` uses `extractApiErrorMessage()` from `app/utils/api-error.ts` and shows the message in a `UAlert` (inside the modal for delete dialogs).
- **Pages**: each resource kind has a list page (`/things`) and a detail page (`/things/[id]`). Follow the existing pages for structure. Each detail page and the sheet editor also have `/<section>/:owner/:readableId[/edit]` routes, added by the `pages:extend` hook in `nuxt.config.ts`. Detail pages fetch with `useResourceFetch` (by whichever form the URL uses, then by UUID) and call `useReadableAddress`, which rewrites a UUID address to the readable one with `history.replaceState` after mount; links the app renders and offers to copy keep UUIDs. `ContentDetail` takes a `section` prop, not `id`; use the fetched `item.id` for changes.
- **Logged-out visitors** can view Public systems, content types, sheets, content, and characters (pages and GET endpoints), read-only. Campaigns, groups, the sheet editor, and the dashboard need an account: those pages use `middleware: "auth"` and their endpoints `requireAuthenticatedUser`, even for Public campaigns. Public pages get `const loggedIn = await useLoggedIn()` and hide what needs an account ("New ..." buttons); edit controls are already hidden by `canEdit`. A detail page whose fetch finds nothing sends a logged-out visitor to sign in (`signInRoute(route.fullPath)`), since their account may be able to see it; `/?redirect=<path>` returns them afterwards, accepted only if `safeRedirectPath` (`shared/sign-in-redirect.ts`) allows it. The sidebar in `app/app.vue` (Nuxt UI's dashboard sidebar, a drawer on phones) groups the nav as Play and Build when logged in and as one Browse group of public items when logged out, with Sign in at the bottom; the signed-out landing page has no sidebar, and the sheet editor starts with it collapsed. Pages wrap their content in `<PageContainer>` for the shared width and padding. Logged in, the sidebar footer shows `UserMenu` (avatar and name dropdown with who is signed in, Profile, Sign out); it reads the profile through `useProfile`, keyed `"profile"` and shared with the profile page, so refreshing it there updates it. `/content/[id]` and `/characters/[id]` share `app/components/ContentDetail.vue`. `/` is the sign-in/register form when logged out and a welcome dashboard when logged in, fed by `GET /api/dashboard`: recently updated Campaigns the user or their Groups own or that the user is a member of, and Characters/Content owned by the user or their Groups. Public or merely shared items are deliberately excluded.
- A lone "username"-like text field inside a `<form>` makes Firefox autofill saved logins (it ignores `autocomplete="off"`); see the add-member row in `app/pages/groups/[id].vue`.

## User-facing copy (moved from CLAUDE.md)

User-facing text is anything a person reads outside the code and git history: UI text, `README.md`, and `docs/`. The team writes the copy that says what Soul Tabletop is or speaks to its users; agents write only the functional and technical parts.

- **Agents may write:** labels, button text, field hints and placeholders, column headers, short status, validation, and error messages, and one-line empty states that say what's missing (e.g. "No campaigns yet."). Technical documentation is fine too: setup, commands, environment variables, architecture, API and Sheet-markup reference.
- **Agents don't write:** project descriptions, taglines, welcome or onboarding text, feature pitches or other promotional copy, announcements, emails, or any other longform text addressed to users. Where a feature needs such text, leave a clearly marked placeholder (`<!-- Copy: … (written by the team) -->` in Markdown; in the UI, a short neutral stand-in like "Welcome text goes here" plus a `// Copy: written by the team` comment), and tell the user it's waiting for them.
- **Team copy lives in `content/copy.yml`**, not inline in components; read "Team copy" in `.claude/conventions.md` before adding to it. Functional text stays in components.
- **Resource names are lowercase mid-sentence** (system, campaign, content type, sheet, content, character, group, resource): "Could not save sheet.", "No content types for this system yet." Labels, titles, buttons, table headers, and nav keep Title Case: "New Sheet", "Delete Content Type", "Back to Sheets", "Content Types". This covers UI text, server error messages, the API reference (OpenAPI summaries/descriptions), and docs. In text people read, write "content type", never `ContentType`.
- Don't rewrite or "improve" copy the team wrote; point out issues (typos, outdated facts) instead. Correcting a fact in technical docs is fine.
- When unsure which side something falls on, ask.
- **Art is the team's too (user, 2026-10-05):** agents don't draw icons, glyphs, illustrations, or other art, including hand-written SVG paths. Use icons from the bundled sets (Lucide, game-icons.net) or a text character, and where a custom drawing is needed, leave a marked placeholder and tell the user.
