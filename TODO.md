# Soon

- **Address any resource by owner + readable ID** · feature · mostly decided (below)
  Not only by UUID, across the whole API (and page URLs). Resource readable IDs are unique per owner and kind (`resource_user_readable_id_kind_unique`/`resource_group_readable_id_kind_unique`), so a readable ID alone isn't enough: a lookup needs the owner too, e.g. `/api/sheet/lucy/fighter`. Decided:
  - **Usernames and group readable IDs share one namespace** (if doable without large rewrites), so an owner readable ID alone says whose resource it is and paths need no `u/`/`g/` prefix. Needs a migration that finds existing collisions between `user_profile.username` and `group.readable_id` (resolve by hand if any), a check on both sides (username availability and registration, group create and rename) against the other table, and ideally one DB-level guarantee (e.g. a shared `owner_readable ID` table both reference, or triggers) rather than two app-level checks that can race.
  - **Visible URLs use readable IDs, links use UUIDs.** Internal links, and any link the UI offers to copy, keep using UUIDs so they never break on renames. When a page is opened by UUID, it rewrites the address bar to the readable ID form (e.g. `/sheets/<id>` → `/sheets/lucy/fighter`, with `history.replaceState`/`navigateTo(..., { replace: true })`, no reload). Readable ID URLs must also resolve when opened directly. Note the tradeoff: a URL copied from the address bar is the readable ID form and breaks if the owner or readable ID is renamed, unless old readable IDs are kept as redirects.
  - Keep UUID routes working everywhere (API and pages); resolve readable IDs case-insensitively (the unique indexes use `lower(readable_id)`). Bodies that reference other resources (`systemId`, `contentTypeId`, content field references) could accept the same owner/readable ID form later.

- **Indexed content fields** · feature · needs decision: real database index or just filterable · depends on: list filters, schema key rename
  Let a content type's schema mark `data` fields as indexed, so lists of that type's content can filter and show them (e.g. a spell list filtered by level or school, or with those as columns). Mark the field in the schema (`ContentFieldSchema` in `shared/content-schema.ts`, its TypeBox mirror `contentTypeSchemaSchema` in `server/utils/api-schemas.ts`, and the schema builder in `app/components/schema/`; keep them in sync), limited to types that can be filtered sensibly (string, number, boolean, and probably scalar; not struct, object, or arrays). - **Caching for resource read requests** · feature · needs decision: which layer, which endpoints, how long; measure first
  Either between the database and the server (e.g. Nitro's `defineCachedFunction`/`cachedEventHandler` with a shared store, since Vercel functions don't share memory) or between the API and the frontend (`Cache-Control` with `s-maxage`/`stale-while-revalidate` on Vercel's CDN, or `ETag`/`304` from `updatedAt`). A first candidate: cache the JSON of GETs for Public resources. Watch out for per-viewer fields in responses (`canEdit`, `canChangeOwner`, content `links` filtered to what the viewer can read): cache only a viewer-independent part and add those per request, or cache only anonymous responses (pairs with the logged-out viewing item). Invalidate on every change that affects a cached response: PATCH/DELETE, Visibility or owner changes, grants, and changes to referenced resources (a content type's schema, a sheet's default). Decide which layer, which endpoints, and how long entries live, and measure first whether reads are slow enough to need it.
- **Let Characters and Content change their content type** · feature · needs decision: whether the new type may be in another content category

A key in both schemas with a different field type (e.g. `level` number → string) is converted when that's safe (number → string, a single value into an `array` of that type, and similar lossless cases) and dropped otherwise, and the warning lists converted and dropped fields separately. Open question: may the new type be in another content category (moving the item between the Characters and Content pages), or only the same group?

# Low priority

- **TypeBox-based OpenAPI generation** · chore · needs decision: which approach
  Generate the OpenAPI request schemas from the TypeBox schemas in `server/utils/api-schemas.ts` instead of writing them by hand in each route's `defineRouteMeta`. Worth doing eventually: today every request body is described twice, and the two drift.
  Likely hard: an earlier attempt found that Nitro reads `defineRouteMeta` statically at build time (it extracts the object literal from the source, without running the route file), so the meta can't reference an imported TypeBox schema or call a function to build one. Approaches to weigh: a build step or script that writes the schemas into the route files or a generated module the meta doesn't need to import; serving our own spec route that merges TypeBox schemas into Nitro's generated spec (e.g. keyed by route and method). A test that checks the hand-written meta against the TypeBox schemas would catch drift but keeps the duplication, so it's a stopgap, not the fix.
- **Catch undeclared imports with ESLint** · chore
  Use ESLint's `import/no-extraneous-dependencies`: server code imported `h3` for a long time without declaring it, and nothing flagged it until code ran outside Nuxt. Check that the rule works with Nuxt's auto-imports and aliases (`~`, `#imports`), and with the hoisted layout if that is ever revisited (see `CLAUDE.md`).

# Before launch

Not soon, but required before any public launch.

- **Group invite approval** · feature · build together with the friends list
  When a non-site-admin adds someone to a Group, create a pending invite the invited user must accept instead of adding them directly. Site admins can still add users directly. Currently `POST /api/group/[id]/members` adds immediately. Required before launch, so nobody can be put in a group without agreeing.
- **Friends list with friend requests** · feature · needs decision: what being friends allows · build together with group invite approval
  Users send friend requests that the other user accepts or declines, and can remove friends. Shares its building blocks with group invites, so design them once: a pending request or invite record (who, to whom, for what, status), accept/decline endpoints, a place to see incoming requests and invites (e.g. a profile or header panel), and probably notifications. Decide what friendship is for, e.g. picking friends when adding group or campaign members or sharing a resource, sharing with all friends at once, and whether people can see each other's friends.
- **Code ownership audit (major).** Much of the code was written with AI agents; before launch, the team (Lucy first) must understand it well enough to own it: maintain it, debug it, and judge changes to it without an agent. Go through the whole codebase area by area (data model and migrations, access control, auth, API routes and validation, the Sheet system in `shared/sheet/`, the Vue pages and components, deployment and env), read it, ask questions until each part makes sense, and simplify or rewrite anything that stays opaque. Agents can help by writing per-area walkthroughs (what it does, why it's built that way, where the risks are) and answering questions, but the understanding has to end up with the team. Pair it with a security review of the whole app and filling test gaps found along the way. Track which areas are done here.
- **Launch review and QA**, in this order, each step fixing what it finds before the next starts:
  1. **Code review of the whole codebase**: correctness, security (access checks on every endpoint, auth, Sheet CSS scoping, input validation), data integrity, and dead or duplicated code. Pairs with the code ownership audit above.
  2. **Automated QA of the running app**: browser tests driving the real app end to end (sign-up and sign-in, creating and editing every resource kind, sharing and visibility, sheets in view and edit mode, group roles), as a suite in the repo that runs against a dev or preview deployment and cleans up after itself. Also an agent exploring the app in a headless browser for issues scripted tests can't catch: broken or odd-looking layouts, confusing states, errors in the console, and flows nobody wrote a test for.
  3. **Manual QA by a person**: clicking through the app on desktop and phone, light and dark mode, and the main browsers, for the things automated tests miss (layout, wording, confusing flows).
