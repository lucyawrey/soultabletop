Before launch, at minimum: a **production database that agents never touch** (its connection string only in Vercel's Production environment, never in any `.env.local`, never pulled to a machine agents run on, and migrations applied to it only by the user, deliberately), and a **development database** for localhost, preview deployments, and agent test runs (so test users, throwaway rows, and `pnpm db:migrate` runs stay out of production). Neon branches fit this: create the dev branch from production (or from a scrubbed copy) and point Preview and Development at it. Things to settle: how migrations reach production (e.g. the user runs `pnpm db:migrate` against it, or a deploy step) and in what order relative to a deploy; whether parallel agents that change the schema each get their own Neon branch (this lifts the "one schema-changing branch at a time" rule in `CLAUDE.md`'s "Parallel work"); how the dev branch is refreshed or reset; and updating `README.md` (env vars, `vercel env pull`), `CLAUDE.md` ("Deployment and database", "Running commands", the `.env.local` rules), `.claude/deployment.md`, `.claude/running-commands.md`, and the agent briefs so nothing agent-facing holds the production URL. Also decide on backups for production (Neon's point-in-time restore window).
- **Group invite approval** · feature · build together with the friends list
  When a non-site-admin adds someone to a Group, create a pending invite the invited user must accept instead of adding them directly. Site admins can still add users directly. Currently `POST /api/group/[id]/members` adds immediately. Required before launch, so nobody can be put in a group without agreeing.
- **Friends list with friend requests** · feature · needs decision: what being friends allows · build together with group invite approval
  Users send friend requests that the other user accepts or declines, and can remove friends. Shares its building blocks with group invites, so design them once: a pending request or invite record (who, to whom, for what, status), accept/decline endpoints, a place to see incoming requests and invites (e.g. a profile or header panel), and probably notifications. Decide what friendship is for, e.g. picking friends when adding group or campaign members or sharing a resource, sharing with all friends at once, and whether people can see each other's friends.
- **Code ownership audit (major).** Much of the code was written with AI agents; before launch, the team (Lucy first) must understand it well enough to own it: maintain it, debug it, and judge changes to it without an agent. Go through the whole codebase area by area (data model and migrations, access control, auth, API routes and validation, the Sheet system in `shared/sheet/`, the Vue pages and components, deployment and env), read it, ask questions until each part makes sense, and simplify or rewrite anything that stays opaque. Agents can help by writing per-area walkthroughs (what it does, why it's built that way, where the risks are) and answering questions, but the understanding has to end up with the team. Pair it with a security review of the whole app and filling test gaps found along the way. Track which areas are done here.
- **Launch review and QA**, in this order, each step fixing what it finds before the next starts:
  1. **Code review of the whole codebase**: correctness, security (access checks on every endpoint, auth, Sheet CSS scoping, input validation), data integrity, and dead or duplicated code. Pairs with the code ownership audit above.
  2. **Automated QA of the running app**: browser tests driving the real app end to end (sign-up and sign-in, creating and editing every resource kind, sharing and visibility, sheets in view and edit mode, group roles), as a suite in the repo that runs against a dev or preview deployment and cleans up after itself. Also an agent exploring the app in a headless browser for issues scripted tests can't catch: broken or odd-looking layouts, confusing states, errors in the console, and flows nobody wrote a test for.
  3. **Manual QA by a person**: clicking through the app on desktop and phone and in the main browsers, for the things automated tests miss (layout, wording, confusing flows).
