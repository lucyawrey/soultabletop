# Improvements

- **(Important)** Current-system selector in the header: a dropdown to pick the system most pages are filtered by, defaulting to "All Systems". Filters every list tied to a system (campaigns and content types directly; sheets, characters, and content through their content type) and the search above, and new-resource forms preselect it. The dashboard ignores it. Opening a resource that belongs to a different system while a specific system is selected switches the selector to that system. Decide where the choice is kept (per browser, e.g. a cookie so SSR renders the filtered list, or per account) and how list endpoints take it (e.g. `?systemId=`).
- Sheet system follow-ups (design in `docs/sheet-system.md`, phase 9): formulas (a safe expression language for computed values), image uploads, dice-roll buttons, and dark-mode syntax colors in the Sheet editor.
- Make `live`, `locked`, and `display` work on `<Tab>` and `<RowDetails>`. The registry accepts them there (`commonAttrs` in `shared/sheet/registry.ts`), so `<Tab display="text">` validates with no diagnostic, but has no effect: those tags are rendered by their parents (`sheet/Tabs.vue`, `sheet/Table.vue`) and never reach `provideSheetFlags` in `sheet/Node.vue`. Either provide the flags where those parents render them, or stop accepting the attributes on those two tags so the editor's Problems list reports them.
- Make the Edit button and the Edit switch on content and character pages less ambiguous. Both say "Edit" (`app/components/ContentDetail.vue`): the button opens a dialog for the record's own details (name, ID, visibility, owner, sheet), while the switch turns the sheet's fields editable in place (the Autosave switch beside it belongs to that). People can't tell which does what. Decide the wording and layout: e.g. rename the button ("Edit Details", "Settings") and/or the switch ("Edit Sheet", "Edit Fields"), or group the switches with the sheet and the button with the page header. The Sheet editor's own "Edit" naming (`/sheets/[id]/edit`, which edits the sheet's markup) and the per-Sheet "Default edit mode" setting should follow whatever names are chosen.
- Sheet features found missing while building the D&D 2024 character sheet (2026-09-30; the test sheet's files are local only):
  - **Formulas matter most** (already in the follow-ups above): every ability modifier, skill bonus, saving throw, passive Perception, spell save DC, and spell attack bonus is typed in by hand. Formulas should cover these cases: a modifier from a score, a bonus from modifier + proficiency bonus by training, and values shown with a sign.
  - **Hide a field's label**: `label=""` falls back to the schema label, so a field inside a titled `Section` repeats the title, and compact rows (a skill's training select) can't drop theirs. E.g. a `hideLabel` attribute, or make an explicit empty `label` mean none.
  - **Stable CSS hooks inside fields**: only a field's root has a hook class (`sheet-number`, ...). Add hooks for its label and value (e.g. `sheet-field-label`, `sheet-field-value`), so Sheet CSS doesn't have to target `div:first-child` or Tailwind classes like `.text-3xl`.
  - **Signed format on `Number`**: only `Value` has `format="signed"`, so editable modifiers show "3", not "+3".
  - **Conditional display**: show or hide a tag by a field's value (e.g. an `if="{path}"` attribute), to hide the Spells tab for non-casters or spell levels with no slots.
  - **Choice fields in schemas**: a string limited to listed options (size, alignment, skill training, spellcasting ability). Today the options live only in the markup's `Select`, so saved data isn't checked, and the generated sheet shows a plain text input.
  - **Default values in schemas**: e.g. size "Medium", or arrays that start with rows. `defaultContentData` only fills empty values for required fields.
  - **Tables for fixed rows**: `Table` binds only arrays, so a fixed set like the 18 skills (a `struct` of structs) needs one small `Grid` each. E.g. let `Table`/`List` iterate a struct's entries.
  - **Compact checkbox in text display**: a boolean shows "✓ Yes" / "✗ No" under its label; proficiency marks need an icon-only or dot variant.
- Make Campaigns places to play, not just records (the biggest gap for playing online). Today a Campaign page (`app/pages/campaigns/[id].vue`) shows only its name, system, and members, and there's no realtime code anywhere. Needed: attaching characters (and other content) to a Campaign; a session view for the Campaign's members; a shared chat and dice log (rolls from sheet dice buttons, see the sheet follow-ups, post there); and realtime sync so members see chat, rolls, and character changes without reloading. Decide the realtime transport early: Vercel functions can't hold WebSockets, so this likely means a hosted realtime service or Postgres-backed polling/SSE, which affects cost.
- Publish the Sheets skill so others can install it with the `skills` CLI (`npx skills add …`). The CLI isn't a package registry: it installs straight from a GitHub repo by finding folders that contain a `SKILL.md` (see `source`/`skillPath` in `skills-lock.json`), so publishing may just mean keeping the skill in this public repo, e.g. `npx skills add lucyawrey/soultabletop -s soul-tabletop-sheets`. Figure out (the skill is at `.claude/skills/soul-tabletop-sheets/`, with `references/`): whether the CLI finds skills under `.claude/skills/` or needs a top-level `skills/` folder (try `npx skills add lucyawrey/soultabletop -l`), whether it should live in a separate repo so installs don't pull this app's other skills, and whether skills.sh needs anything to list it.
- Moving values when a schema key is renamed: today renaming a field key in the schema builder leaves existing content's values under the old key (and strict content types then reject that content on its next save). Options: detect renames in the builder (it knows the field's stable id) and have `PATCH /api/content-type/[id]` rewrite `content.data` for that type in the same transaction, or offer a "rename key" action separate from editing the key.
- Figure out caching for resource read requests, either between the database and the server (e.g. Nitro's `defineCachedFunction`/`cachedEventHandler` with a shared store, since Vercel functions don't share memory) or between the API and the frontend (`Cache-Control` with `s-maxage`/`stale-while-revalidate` on Vercel's CDN, or `ETag`/`304` from `updatedAt`). A first candidate: cache the JSON of GETs for Public resources. Watch out for per-viewer fields in responses (`canEdit`, `canChangeOwner`, content `links` filtered to what the viewer can read): cache only a viewer-independent part and add those per request, or cache only anonymous responses (pairs with the logged-out viewing item). Invalidate on every change that affects a cached response: PATCH/DELETE, Visibility or owner changes, grants, and changes to referenced resources (a content type's schema, a sheet's default). Decide which layer, which endpoints, and how long entries live, and measure first whether reads are slow enough to need it.
- User API keys, so scripts, agents, and other tools can call the API as a user. Better Auth has an API key plugin (check it fits: keys stored hashed, shown once at creation, optional expiry, revocable, rate limits, maybe per-key permissions such as read-only). Needs a page under the user's profile to create, name, and revoke keys; `getAuthenticatedUser` accepting a key (e.g. `Authorization: Bearer …` or `x-api-key`) alongside the session cookie; CSRF/origin checks that don't block key-authenticated requests; and API reference docs for authenticating.
- Address any resource by owner + readable ID, not only by UUID, across the whole API (and page URLs). Resource readable IDs are unique per owner and kind (`resource_user_readable_id_kind_unique`/`resource_group_readable_id_kind_unique`), so a readable ID alone isn't enough: a lookup needs the owner too, e.g. `/api/sheet/lucy/fighter`. Decided:
  - **Usernames and group readable IDs share one namespace** (if doable without large rewrites), so an owner readable ID alone says whose resource it is and paths need no `u/`/`g/` prefix. Needs a migration that finds existing collisions between `user_profile.username` and `group.readable_id` (resolve by hand if any), a check on both sides (username availability and registration, group create and rename) against the other table, and ideally one DB-level guarantee (e.g. a shared `owner_readable ID` table both reference, or triggers) rather than two app-level checks that can race.
  - **Visible URLs use readable IDs, links use UUIDs.** Internal links, and any link the UI offers to copy, keep using UUIDs so they never break on renames. When a page is opened by UUID, it rewrites the address bar to the readable ID form (e.g. `/sheets/<id>` → `/sheets/lucy/fighter`, with `history.replaceState`/`navigateTo(..., { replace: true })`, no reload). Readable ID URLs must also resolve when opened directly. Note the tradeoff: a URL copied from the address bar is the readable ID form and breaks if the owner or readable ID is renamed, unless old readable IDs are kept as redirects.
  - Keep UUID routes working everywhere (API and pages); resolve readable IDs case-insensitively (the unique indexes use `lower(readable_id)`). Bodies that reference other resources (`systemId`, `contentTypeId`, content field references) could accept the same owner/readable ID form later.
- ID display: remove the ID column from list pages; on detail pages, move the readable ID from under the name heading to beside it, in a small rounded box (e.g. a `UBadge`-like pill).
- Live readable ID availability: the profile page checks a username as soon as it changes (debounced, with an "available"/"in use" hint). Carry that to the sign-up username field and to every resource and group readable ID field (`ReadableIdField`, create and edit forms). Probably one shared composable plus a check endpoint per kind, scoped to the owner and kind since resource readable IDs are unique per owner and kind; the server stays the authority (409 on conflict).
- Change password from the profile page: a "Change Password" section on `/profile` with current password, new password, and confirm new password. Better Auth's email/password support already provides a change-password call on the auth client (`app/utils/auth-client.ts`; check the exact name and whether it can revoke the user's other sessions, which should be an option, on by default). The new password must follow the same rules as registration, which today are Better Auth's defaults (`emailAndPassword` in `server/utils/auth.ts` sets nothing else), so check them and show the rules on both forms. Errors (wrong current password, too short) go through `extractApiErrorMessage` into a `UAlert`, and the form clears after success. Password reset by email is a separate feature (it needs email sending, which the app doesn't have).
- Show the system everything belongs to. Campaigns and Content Types show their system on detail pages, but Sheets, Content, and Characters reach a system only through their content type and never show it. Add a System column to their list pages and a system link on their detail pages (have the list/single GETs return `systemId`, or join client-side), and make every content type or resource dropdown and picker (create forms, `ContentPicker`, `ResourcePicker`) show the system, e.g. "Fighter (D&D 2024)" or options grouped by system. Related to the current-system selector: labels matter most when "All Systems" is selected.
- Let Characters and Content change their content type, not just their Sheet. `PATCH /api/content/[id]` accepts `contentTypeId` (edit access to the Content, read access to the new type); data keeps every key present in both schemas, drops keys the new type doesn't have if it's strict (keeps them all otherwise), and fills new required fields with empty values as `defaultContentData` does; the Sheet resets to the new type's default. The UI confirms first with a warning listing the fields that will be dropped. A key in both schemas with a different field type (e.g. `level` number → string) is converted when that's safe (number → string, a single value into an `array` of that type, and similar lossless cases) and dropped otherwise, and the warning lists converted and dropped fields separately. Open question: may the new type be in another content category (moving the item between the Characters and Content pages), or only the same group?
- Print Content: a Print button on the Content detail page (`ContentDetail.vue`) calling `window.print()`, plus print styles that hide the app chrome and print just the rendered sheet. Decide in `docs/sheet-system.md` whether Sheet CSS may use `@media print`.
- Onboarding for new users (test users were unsure what a "game" is): a Getting Started page or dashboard panel explaining the concepts (system, content type, sheet, content, campaign) with links, and next-step suggestions in empty states and after creating something (e.g. a new system's page offers "Add a Content Type"). Agents build the structure and button labels; the explanations and welcome text are written by the team (placeholders until then).
- Official D&D 2024 system with open content (large): owned by the `soul` group, built on the SRD 5.2 (CC-BY-4.0, so the system page needs the required attribution notice). Official content types (character, spell, monster, item, …), a character sheet and stat-block/card sheets, and the SRD content itself as Official resources. Check the license of any source used beyond the SRD document itself. Depends on user API keys, the Sheets agent skill, and likely the authoring CLI below, so the system can be authored as files and uploaded; the sheet follow-ups (formulas, dice buttons) are wanted too.
- Authoring CLI for uploading resources from files on disk, authenticated with a user API key: systems, content types, sheets, and content defined as files (JSON or TOML, to decide, for resource metadata, schemas, and content data; the existing `.stts` markup and `.css` files for sheets) in a defined folder layout, which the CLI creates or updates through the API. Makes bulk authoring (e.g. the official D&D 2024 system) possible in an editor, under version control, and by agents. Files identify resources by owner + readable ID, not ID, both for themselves and for references to other resources (a content type's system, a sheet's content type, content references), so they can be written before anything exists in the database and never need IDs written back into them; the CLI creates a resource when its owner + readable ID doesn't exist yet and updates it otherwise. This depends on the readable ID addressing item (API lookups by owner + readable ID, and bodies accepting owner/readable ID references). Decide: the file format and folder layout, whether it can also download resources to files, and where the CLI lives (in this repo or a published package).
- Have all copy pull from an external data file for sharing across pages and easy updating.

# Before launch

Not soon, but required before any public launch.

- **Code ownership audit (major).** Much of the code was written with AI agents; before launch, the team (Lucy first) must understand it well enough to own it: maintain it, debug it, and judge changes to it without an agent. Go through the whole codebase area by area (data model and migrations, access control, auth, API routes and validation, the Sheet system in `shared/sheet/`, the Vue pages and components, deployment and env), read it, ask questions until each part makes sense, and simplify or rewrite anything that stays opaque. Agents can help by writing per-area walkthroughs (what it does, why it's built that way, where the risks are) and answering questions, but the understanding has to end up with the team. Pair it with a security review of the whole app and filling test gaps found along the way. Track which areas are done here.
- **Launch review and QA**, in this order, each step fixing what it finds before the next starts:
  1. **Code review of the whole codebase**: correctness, security (access checks on every endpoint, auth, Sheet CSS scoping, input validation), data integrity, and dead or duplicated code. Pairs with the code ownership audit above.
  2. **Automated QA of the running app**: browser tests driving the real app end to end (sign-up and sign-in, creating and editing every resource kind, sharing and visibility, sheets in view and edit mode, group roles), as a suite in the repo that runs against a dev or preview deployment and cleans up after itself. Also an agent exploring the app in a headless browser for issues scripted tests can't catch: broken or odd-looking layouts, confusing states, errors in the console, and flows nobody wrote a test for.
  3. **Manual QA by a person**: clicking through the app on desktop and phone, light and dark mode, and the main browsers, for the things automated tests miss (layout, wording, confusing flows).

# Post launch

- Prepare for dual licensing (low priority): the plan is MIT for most of the app plus a smaller set of proprietary premium features. Code already released under MIT stays MIT, so premium features will live in their own folder of all-new code under a separate license. Before accepting outside contributions, add a contributor license agreement (CLA) so contributed code can be relicensed; without one, each contributor keeps the copyright on their code. Also decide how the premium folder is licensed and marked (its own LICENSE file, headers) and how the MIT app loads it.
