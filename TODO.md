# Improvements

- **(Important)** Search, and split each resource list page into **My <Resources>** and **Find <Resources>** tabs (e.g. "My Sheets" / "Find Sheets"). "My" lists what the user or their groups own (decide whether resources merely shared with them belong there too); "Find" searches public resources. Logged-out visitors get only the Find tabs (see the logged-out viewing item). Needs server-side search on list endpoints (e.g. `?q=` over name and slug, plus `?scope=mine|public`, with pagination instead of returning everything), a search box on each tab, and the tab kept in the URL so it survives reloads and links. Results show whether they're **Official** (owned by a system group) or **Community** (everything else), and Official results rank first.
- **(Important)** Current-system selector in the header: a dropdown to pick the game system most pages are filtered by, defaulting to "All Systems". Filters every list tied to a system (games and content types directly; sheets, characters, and content through their content type) and the search above, and new-resource forms preselect it. The dashboard ignores it. Opening a resource that belongs to a different system while a specific system is selected switches the selector to that system. Decide where the choice is kept (per browser, e.g. a cookie so SSR renders the filtered list, or per account) and how list endpoints take it (e.g. `?systemId=`).
- Sheet system follow-ups (design in `docs/sheet-system.md`, phase 9): formulas (a safe expression language for computed values), image uploads, dice-roll buttons, and dark-mode syntax colors in the Sheet editor.
- Make Games places to play, not just records (the biggest gap for playing online). Today a Game page (`app/pages/games/[id].vue`) shows only its name, system, and members, and there's no realtime code anywhere. Needed: attaching characters (and other content) to a Game; a session view for the Game's members; a shared chat and dice log (rolls from sheet dice buttons, see the sheet follow-ups, post there); and realtime sync so members see chat, rolls, and character changes without reloading. Decide the realtime transport early: Vercel functions can't hold WebSockets, so this likely means a hosted realtime service or Postgres-backed polling/SSE, which affects cost.
- Sheet detail page (`/sheets/[id]`, the non-edit view) should preview the rendered Sheet instead of only showing its raw markup and CSS: render it with `SheetRenderer` against sample data from `sampleSheetData` (not tied to any Content), with its scoped CSS and broken-tag placeholders for editors, like the editor's preview. Keep the raw markup/CSS available (e.g. collapsed or in a tab). `GET /api/sheet/[id]` already returns the `schemas` this needs.
- Import/export Sheet markup and CSS as files, for authoring outside the site: in the Sheet editor, "Upload" buttons for the Markup and CSS tabs (and drag-and-drop onto the editor) that load a local text file (e.g. `.sheet`/`.xml`/`.html` for markup, `.css`) into the editor as an unsaved change, so it's checked and previewed before saving; plus "Download" buttons to export the current markup/CSS. Read files client-side (`FileReader`/`file.text()`, no server storage), cap size at the existing limits (100 KB markup, 50 KB CSS), and reject non-text files.
- Choose how non-editable fields look: plain text (today's view mode, good for stat blocks like a Fireball spell) or their usual field boxes, disabled/read-only (good for character sheets that should look the same in and out of Edit mode). Likely an inherited attribute like `live`/`locked` (e.g. `display="text" | "box"` on any tag, applying to fields inside) plus a per-Sheet default in the Sheet editor's Settings (a new `sheet` column; generated sheets pick a default by content category). Applies to Edit off, `locked` fields before unlocking, and values reached through references. Registry: `shared/sheet/registry.ts` `commonAttrs`; rendering: `sheet/Field.vue`/`FieldInput.vue`, flags via `provideSheetFlags` in `useSheet.ts`.
- Agent skill for authoring Soul Tabletop Sheets: add `.claude/skills/soul-tabletop-sheets/SKILL.md` so an agent can help users and devs write Soul Tabletop Sheet markup and CSS files. Its name and description should say plainly that it's for Soul Tabletop's own Sheet format (so agents don't confuse it with other character-sheet systems or plain HTML/CSS) and trigger on requests about Soul Tabletop sheets, character sheets, or stat blocks for this app. Cover: the markup syntax (tags, attributes, `{path}` interpolation, escapes, comments), every tag with its attributes and allowed children (generate from or point at `shared/sheet/registry.ts` so it can't drift), field paths (List scope, `/`, `.`, `content` fields up to 3 hops, built-in `name`), `live`/`locked`, CSS rules (scoping, `sheet-<tag>` hook classes, `:root`, `.dark`, what's rejected, curated fonts, Nuxt UI tokens), how to read a ContentType schema to pick fields, worked examples (character sheet, NPC stat block, spell/item card), and how to check work (`compileSheet`/`processSheetCss` via a small script or test, or the editor's Problems list). For now authors paste or upload the resulting markup/CSS into the Sheet editor themselves (see the file import/export item above); later the agent could use the API directly.
- Publish the Sheets skill so others can install it with the `skills` CLI (`npx skills add …`). The CLI isn't a package registry: it installs straight from a GitHub repo by finding folders that contain a `SKILL.md` (see `source`/`skillPath` in `skills-lock.json`), so publishing may just mean keeping the skill in this public repo, e.g. `npx skills add lucyawrey/soultabletop -s soul-tabletop-sheets`. Figure out: whether the CLI finds skills under `.claude/skills/` or needs a top-level `skills/` folder (try `npx skills add lucyawrey/soultabletop -l`), whether it should live in a separate repo so installs don't pull this app's other skills, and whether skills.sh needs anything to list it.
- Moving values when a schema key is renamed: today renaming a field key in the schema builder leaves existing content's values under the old key (and strict content types then reject that content on its next save). Options: detect renames in the builder (it knows the field's stable id) and have `PATCH /api/content-type/[id]` rewrite `content.data` for that type in the same transaction, or offer a "rename key" action separate from editing the key.
- Let logged-out visitors view public resources, and hide header nav items they can't use. Today every list and detail page uses `middleware: "auth"`, so anonymous visitors are redirected even to Public resources. The API is partly ready: the list and single GETs for systems, games, content types, and sheets already allow anonymous callers through `getResourceAccessOrPublic` (Public only); content (`/api/content`, `/api/content/[id]`, which also covers characters) and groups require sign-in. Decide which kinds anonymous visitors can see (likely systems, content types, sheets, and Public content/characters; not groups, games' members, or the dashboard), open those pages and endpoints to them read-only (no create/edit/delete controls, no Edit/Autosave switches), keep the rest behind sign-in, and show only the matching nav links in the header (desktop and mobile `#body` in `app/app.vue`) when logged out.
- User API keys, so scripts, agents, and other tools can call the API as a user. Better Auth has an API key plugin (check it fits: keys stored hashed, shown once at creation, optional expiry, revocable, rate limits, maybe per-key permissions such as read-only). Needs a page under the user's profile to create, name, and revoke keys; `getAuthenticatedUser` accepting a key (e.g. `Authorization: Bearer …` or `x-api-key`) alongside the session cookie; CSRF/origin checks that don't block key-authenticated requests; and API reference docs for authenticating.
- Address any resource by slug, not only by ID, across the whole API (and page URLs). Resource slugs are unique per owner and kind (`resource_user_slug_kind_unique`/`resource_group_slug_kind_unique`), so a slug alone isn't enough: a lookup needs the owner too, e.g. `/api/sheet/lucy/fighter`. Decided:
  - **Usernames and group slugs share one namespace** (if doable without large rewrites), so an owner slug alone says whose resource it is and paths need no `u/`/`g/` prefix. Needs a migration that finds existing collisions between `user_profile.username` and `group.slug` (resolve by hand if any), a check on both sides (username availability and registration, group create and rename) against the other table, and ideally one DB-level guarantee (e.g. a shared `owner_slug` table both reference, or triggers) rather than two app-level checks that can race.
  - **Visible URLs use slugs, links use IDs.** Internal links, and any link the UI offers to copy, keep using IDs so they never break on renames. When a page is opened by ID, it rewrites the address bar to the slug form (e.g. `/sheets/<id>` → `/sheets/lucy/fighter`, with `history.replaceState`/`navigateTo(..., { replace: true })`, no reload). Slug URLs must also resolve when opened directly. Note the tradeoff: a URL copied from the address bar is the slug form and breaks if the owner or slug is renamed, unless old slugs are kept as redirects.
  - Keep ID routes working everywhere (API and pages); resolve slugs case-insensitively (the unique indexes use `lower(slug)`). Bodies that reference other resources (`systemId`, `contentTypeId`, content field references) could accept the same owner/slug form later.
- User profile page (own profile only for now; viewing other users' profiles comes later): a `/profile` page, linked from the header's user menu, to view and edit your username (live availability check via `/api/profile/username-availability`, slug rules as at registration) and icon image URL (https only, with a preview), and to see read-only details like display name, email, site role (Admin/Member), and your groups. The API already exists: `GET`/`PATCH /api/profile` (`profilePatchSchema`: `username`, `iconImageUrl`). Note usernames will share a namespace with group slugs (see the slug addressing item).
- Slug display: remove the Slug column from list pages; on detail pages, move the slug from under the name heading to beside it, in a small rounded box (e.g. a `UBadge`-like pill).
- Have all copy pull from an external data file for sharing across pages and easy updating.
- TypeBox based OpenAPI generation (low priority)
- Investigate switching from Node/pnpm to Bun for development and production (Vercel's Bun runtime is in beta), for faster builds, installs, and server responses on a small budget. Check separately: Bun as package manager (`bun.lock` replacing `pnpm-lock.yaml`, `packageManager`, CI, Vercel install), Bun as the local dev/build runtime (Nuxt/Nitro, Vite, `drizzle-kit`, `vitest`), and Bun as the production runtime on Vercel (how it's enabled, which Nitro preset, whether Better Auth, Drizzle, the Neon driver, and Scalar work on it, cold starts, beta limits, effect on cost). Measure build time and response times against the current setup on a preview deployment before deciding; any step can be adopted alone.
- Group invite approval (low priority): when a non-site-admin adds someone to a Group, create a pending invite the invited user must accept instead of adding them directly. Site admins can still add users directly. Currently `POST /api/group/[id]/members` adds immediately.

# Before launch

Not soon, but required before any public launch.

- **Code ownership audit (major).** Much of the code was written with AI agents; before launch, the team (Lucy first) must understand it well enough to own it: maintain it, debug it, and judge changes to it without an agent. Go through the whole codebase area by area (data model and migrations, access control, auth, API routes and validation, the Sheet system in `shared/sheet/`, the Vue pages and components, deployment and env), read it, ask questions until each part makes sense, and simplify or rewrite anything that stays opaque. Agents can help by writing per-area walkthroughs (what it does, why it's built that way, where the risks are) and answering questions, but the understanding has to end up with the team. Pair it with a security review of the whole app and filling test gaps found along the way. Track which areas are done here.

# Post launch

- Prepare for dual licensing (low priority): the plan is MIT for most of the app plus a smaller set of proprietary premium features. Code already released under MIT stays MIT, so premium features will live in their own folder of all-new code under a separate license. Before accepting outside contributions, add a contributor license agreement (CLA) so contributed code can be relicensed; without one, each contributor keeps the copyright on their code. Also decide how the premium folder is licensed and marked (its own LICENSE file, headers) and how the MIT app loads it.
